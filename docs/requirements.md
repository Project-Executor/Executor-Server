# Executor(집행자) 요구사항 정의서

> 명령을 실행하고, 버그를 제거하라.

| 항목 | 내용 |
| --- | --- |
| 프로젝트 | Executor(집행자): 개발자 컨셉의 그리드 기반 턴제 이동 퍼즐 게임 |
| 기간 | 2026.10.12 ~ 2026.11.24 |
| 클라이언트 | Unity (C#), PC |
| 서버 | Spring Boot 4, Java 17 |

## 1. 용어 정의

| 용어 | 설명 |
| --- | --- |
| 집행자 | 플레이어 캐릭터. 시스템을 복구하기 위해 투입된 존재 |
| 작전 (Operation) | 스테이지의 상위 분류. 스토리의 한 장(章)에 해당 (예: Tutorial, Operation 1) |
| 스테이지 (Stage) | 한 번에 플레이하는 퍼즐 맵 하나 |
| 공식 스테이지 | 관리자가 만든 스토리 스테이지 (`creator_id IS NULL`) |
| 사용자 맵 | 사용자가 맵 에디터로 만든 스테이지 (`creator_id`에 제작자 저장) |
| 턴 (Move) | 이동, 장애물 밀기·부수기 등 한 번의 행동 |
| 기준 턴 (Par) | 별 2개째를 얻기 위한 최대 턴 수 (`par_moves`) |
| 숨겨진 요소 | 스테이지마다 숨겨진 버그(처치) 또는 피스(수집). 별 3개째 조건 |
| 이상 개체 | 맵에 등장하는 오류(버그), 바이러스 등의 적·기믹 |
| 도감 | 이상 개체와 개발 용어를 설명하는 수집 콘텐츠 |
| 코인 | 게임 내 재화. 첫 클리어 보상과 우편으로 얻고 상점에서 사용 |

## 2. 게임 규칙

### 2.1 스테이지 진행

- 상하좌우(W, A, S, D) 입력 한 번이 턴 하나를 소모한다.
- 장애물 방향으로 이동하면 턴을 소모해서 장애물을 부수거나 민다.
- 열쇠 칸에 도착하면 열쇠를 얻고, 열쇠로 문을 연다.
- NPC 주변 3x3 칸 안에 들어가면 대화할 수 있다. 대화 중 선택지에 따라 이야기가 갈린다.
- 목적지(문 아이콘)에 도달하면 클리어한다.
- **턴 제한은 실패 조건이 아니라 별 조건**이다. 기준 턴을 넘겨도 클리어할 수 있다.
- 추격 봇 미니게임에서는 플레이어를 따라오는 봇에 닿으면 게임 오버가 된다.
- 맵 구성(타일, 장애물, 열쇠, NPC, 대화, 봇, 숨겨진 요소, 힌트)은 모두 스테이지의 `map_data`(JSON)에 담는다.

### 2.2 별 평가

| 별 | 조건 | 저장 방식 |
| --- | --- | --- |
| ★1 | 스테이지 클리어 | `user_stages.first_cleared_at IS NOT NULL` |
| ★2 | 기준 턴 이하로 클리어 | `user_stages.best_moves <= stages.par_moves` (계산) |
| ★3 | 숨겨진 버그 처치 또는 피스 수집 | `user_stages.is_hidden_found` |

- 별은 여러 번 도전한 결과가 **누적**된다. 예를 들어 한 번은 기준 턴을 달성하고, 다른 판에서 숨겨진 요소를 찾으면 별 3개가 된다.
- 튜토리얼(`stage_type = TUTORIAL`)은 ★1만 있다.

### 2.3 스테이지 해금

- 공식 스테이지는 **바로 앞 스테이지를 클리어해야** 열린다. 순서는 작전의 `sort_order`, 그다음 스테이지의 `stage_no`로 정한다.
- 튜토리얼 첫 스테이지는 처음부터 열려 있다.
- 공개된 사용자 맵은 해금 조건 없이 누구나 플레이할 수 있다.

## 3. 기능 요구사항

우선순위
- **P0**: 발표회에 반드시 있어야 하는 기능
- **P1**: 핵심 부가 기능
- **P2**: 시간이 남으면 구현할 기능

### 3.1 회원 / 인증 (AUTH)

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| AUTH-01 | 이메일, 비밀번호, 닉네임으로 회원가입한다. 가입하면 `users`와 `profiles` 행을 함께 만든다. | P0 |
| AUTH-02 | 이메일 형식을 검증하고, 중복 이메일은 거부한다. | P0 |
| AUTH-03 | 비밀번호는 8~64자이며 BCrypt로 해시해서 저장한다. | P0 |
| AUTH-04 | 이메일과 비밀번호로 로그인하면 Access Token과 Refresh Token을 발급한다. | P0 |
| AUTH-05 | Refresh Token으로 Access Token을 재발급한다. 재발급할 때 Refresh Token도 새로 바꾼다(Rotation). | P0 |
| AUTH-06 | 로그아웃하면 Refresh Token을 무효화한다. | P0 |
| AUTH-07 | 비밀번호를 다시 확인한 뒤 회원 탈퇴한다. 탈퇴하면 개인 데이터는 삭제되고, 신고 기록은 남되 신고자와 대상이 NULL이 된다. | P1 |
| AUTH-08 | 일반 사용자는 `USER`, 관리자는 `ADMIN` 권한을 가진다. `/api/admin/**`은 `ADMIN`만 호출할 수 있다. | P0 |

### 3.2 프로필 (PROFILE)

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| PROFILE-01 | 닉네임은 2~20자이며 중복될 수 없다. 가입 전에 중복 여부를 확인할 수 있다. | P0 |
| PROFILE-02 | 튜토리얼에서 집행자 이름(`character_name`)을 입력한다. 중복을 허용하고, 대사에 표시된다. | P0 |
| PROFILE-03 | 내 프로필(닉네임, 집행자 이름, 자기소개, 코인, 장착 아이템)을 조회한다. | P0 |
| PROFILE-04 | 닉네임, 집행자 이름, 자기소개(최대 255자)를 수정한다. | P1 |
| PROFILE-05 | 다른 사용자의 공개 프로필(닉네임, 자기소개, 장착 스킨, 클리어 수)을 조회한다. | P1 |
| PROFILE-06 | 닉네임으로 사용자를 검색한다. | P1 |
| PROFILE-07 | 보유한 스킨과 테마를 종류별로 하나씩 장착하거나 해제한다. 해제하면 기본 스킨·테마로 돌아간다. | P1 |

### 3.3 스테이지 / 플레이 (STAGE)

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| STAGE-01 | 작전 목록과 각 작전의 스테이지 목록을 조회한다. 스테이지마다 해금 여부, 클리어 여부, 획득한 별, 최고 기록을 함께 보여준다. | P0 |
| STAGE-02 | 스테이지 상세(맵 데이터, 기준 턴, 보상 코인)를 조회한다. 잠긴 스테이지는 조회할 수 없다. | P0 |
| STAGE-03 | 맵 데이터를 보낼 때 힌트(`hints`)는 빼고 보낸다. 힌트는 힌트 아이템을 써야만 받을 수 있다. | P1 |
| STAGE-04 | 한 판이 끝나면(클리어, 게임 오버, 포기) 결과를 서버에 제출한다. 결과에는 클리어 여부, 사용한 턴 수, 숨겨진 요소 달성 여부, 만난 이상 개체(도감 ID)가 들어간다. | P0 |
| STAGE-05 | 결과를 제출할 때마다 도전 횟수(`play_count`)가 1 늘어난다. | P0 |
| STAGE-06 | 클리어했다면 최소 턴 기록(`best_moves`)을 더 작은 값으로 갱신하고, 숨겨진 요소 달성을 누적한다. | P0 |
| STAGE-07 | **첫 클리어일 때만** 보상 코인을 지급한다. 동시에 요청이 와도 한 번만 지급되어야 한다. | P0 |
| STAGE-08 | 결과 응답에는 이번 별, 누적 별, 최고 기록 갱신 여부, 첫 클리어 보상, 새로 해금된 도감이 들어간다. | P0 |
| STAGE-09 | 스테이지별로 최소 턴 순위를 조회한다. 범위는 전체 또는 친구만 고를 수 있다. 턴이 같으면 먼저 클리어한 사람이 앞선다. | P1 |
| STAGE-10 | 사용한 턴 수는 1 이상 9999 이하만 받는다. | P0 |

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |

| CUSTOM-08 | 내가 만든 맵 목록을 조회한다. | P2 |
| CUSTOM-09 | 내 맵을 삭제한다. 삭제하면 그 맵의 플레이 기록도 함께 삭제된다. | P2 |

## 4. 비기능 요구사항

| ID | 분류 | 요구사항 |
| --- | --- | --- |
| NFR-01 | 보안 | 비밀번호는 BCrypt로 해시하고, 응답과 로그에 절대 남기지 않는다. |
| NFR-02 | 보안 | Access Token 유효기간은 30분, Refresh Token 유효기간은 14일이다. Refresh Token은 Redis에 `refresh:{userId}` 키로 저장하고 TTL을 건다. |
| NFR-03 | 보안 | JWT 서명 키, DB 접속 정보 같은 비밀 값은 Railway 환경 변수로만 넣고 저장소에 커밋하지 않는다. |
| NFR-04 | 보안 | 사용자는 자기 데이터만 수정할 수 있다. 다른 사람의 우편, 맵, 메시지에 접근하면 403을 반환한다. |
| NFR-05 | 무결성 | 코인 증감, 보상 지급, 친구 수락은 트랜잭션으로 처리한다. 중복 지급은 조건부 UPDATE로 막는다. |
| NFR-06 | 무결성 | 테이블 구조는 `schema.sql`이 기준이다. JPA는 `ddl-auto=validate`로 실행한다. 운영 DB 구조 변경은 `db/migrations/`의 SQL로 적용한다. |
| NFR-07 | 일관성 | 모든 시간은 UTC로 저장하고, 응답은 ISO-8601 형식(`2026-11-09T12:00:00Z`)으로 보낸다. |
| NFR-08 | 일관성 | 요청과 응답 JSON의 필드 이름은 camelCase를 쓴다. |
| NFR-09 | 오류 처리 | 모든 오류는 정해진 형식(`status`, `code`, `message`)으로 응답한다. |
| NFR-10 | 오류 처리 | 결과 제출이 네트워크 문제로 실패하면 클라이언트가 결과를 보관해 두었다가 다시 보낸다. 서버는 같은 결과가 다시 와도 보상을 두 번 주지 않는다. |
| NFR-11 | 성능 | 일반 API는 200ms 이내에 응답하는 것을 목표로 한다 (발표회 기준 동시 접속 수십 명 수준). |
| NFR-12 | 문서화 | springdoc으로 Swagger UI(`/swagger-ui/index.html`)를 제공한다. |
| NFR-13 | 배포 | 서버, MySQL, Redis를 모두 Railway에 배포한다. |

## 5. 서비스 계층에서 검증할 규칙

DB 제약만으로는 막을 수 없어서 서버 코드에서 반드시 확인해야 하는 규칙이다. MySQL은 `ON DELETE CASCADE`나 `SET NULL`이 걸린 FK 컬럼을 CHECK 제약에 쓸 수 없기 때문이다.

1. 친구 관계는 `user_id < friend_id`로 정렬해서 저장한다.
2. 친구 요청은 자기 자신에게 보낼 수 없다.
3. 공식 스테이지는 `operation_id`와 `stage_no`가 있어야 하고 `creator_id`는 NULL이다. 사용자 맵은 그 반대이며 `reward_coin = 0`이다.
4. 사용자 맵은 제작자가 클리어한 기록이 있어야 공개할 수 있다.
5. 장착하려는 아이템은 내가 가지고 있어야 하고 종류(SKIN, THEME)가 맞아야 한다.
6. 우편에 첨부 아이템이 없으면 첨부 수량은 0이다.
7. 대상 없이 신고할 수 있는 카테고리는 버그 제보와 기타뿐이다.
